## 致命

### 1. 非 bash 的写入工具会装成 program，同意后按新槽位执行

批评第 2 条要求：存不下输出、效果不能在隔离环境里重放、或工具不是只读的，这一步保持显式模型步，不得标成 `program`。bash 仍按第 16 条可以成为脚本步。审批前不执行。

审批前不执行已经做到。`propose_compiled_procedure` 先 `askApproval`，不同意时返回 `NOT_APPROVED`。用 `write` 走完整插件路径时，审批函数返回前，工具桩的调用列表是空的。

只读限制没有做。`compiler.js` 的 `checkRun` 只区分「bash 必须是脚本」和「其他工具必须是 delegate」。没有只读名单，也不要求 `fileHash`。

行为：

- 两次 `write`（路径都是 `a.txt`，内容分别是 `one` / `two`）再重复一遍。合同把第一步前置写成 `{ argsEquals: { path: "/not/observed" } }`，两次都没有 `fileHash`。`assessCompiledProposal` 返回 `READY`。两步都是 `program` + `delegate`。后置是 `{ exitCode: 0 }`。签名键只有 `constants`、`slots`、`tools`。
- `write` 的内容在两次出现里不同，后接同一条 `echo done`。评估同样是 `READY`。接着按执行器调用，槽位传入观察里没出现过的 `other`，实际调用是 `write { path: "a.txt", contents: "other" }`，然后是 `bash echo done`。
- 插件路径在 `allowed-once` 之后注册 `ec_write_<时间戳>`。再执行这个 `ec_`，桩收到的调用是 `write`、`write`，结果 `ok: true`。撒谎的前置没有挡住安装。

`index.js` 的 `compiledDefinition` 在内层调用上设置 bypass。写入因此也不进摩擦分。

次生影响：

- 摩擦记分：这条写入不加分，也不会把原工具过线。修的时候如果让写入失败去走 `noteCall`，三次失败就会把 `ec_` 或原工具过线；`propose_tool_goal` 又拒绝整份替换 `ec_`，工具会卡住。
- 审批：这种合同现在能弹出卡片。卡片写了「槽位只在两次绑定上有参照」，执行器仍会用新槽位调用原工具。
- 会话隔离：拦截写在当前会话的 `catalog.intercepts`。不要为了拦住写入去改全局工具表。
- 已同意的 `fd_`：内层 bypass 会跳过摩擦闸。bash 上若已有 `fd_` 后继，`look()` 会把编译拦截清出本次判断，`fd_` 仍优先。修写入类程序步时不要把拦截写进 `successor`，否则会盖住已经同意的 `fd_`。
- 桌面开关、GitHub、仓库外依赖：这条不靠安装渠道。旧的 GitHub 包里根本没有这段执行器。

### 2. 失败步交任意输出，后面的程序步会接着跑

批评第 8 条要求恢复时检查这一步的后置，通过才继续。批评第 9 条要求失败步在新版本通过独立验收之前保持模型步。

`markStepAgent` 会立刻把失败步改成 `agent`，并留下原来的后置。默认后置来自 `postFor`：两次退出码都是 0 时就是 `{ exitCode: 0 }`。`executeCompiled` 恢复时先用 `exitCode: null` 套后置，再套一份硬编码的 `exitCode: 0`。第二份把 `{ exitCode: 0 }` 套成功，`step_output` 的正文不参与判断。

行为：三步都是 bash，`echo one`、`echo two`、`echo three`。中间步标成 `agent` 且后置为 `{ exitCode: 0 }` 后，用 `step_output` `not-the-observed-output` 恢复。返回成功，下一条执行的命令是 `echo three`。

插件侧没有要求这次恢复先经过新的审批。`compiledDefinition` 见到 `STEP_FAILED` 只改目录里的 mode，然后下一次带 `resume_token` 就能继续。

次生影响：

- 摩擦记分：`ec_` 调用带 `compiled: true`，`ingestCall` 不计分。这个绕过不会把 `ec_` 过线，也不会把里面的 bash 过线。修后置时不要把失败重新送进 `noteCall`。
- 审批：失败降级本身没有新卡片。真正的修订要到 `revise_step` 才审批。现在可以不修订就跑完后续命令。
- 会话隔离：`resume_token` 存在该会话的 `state.resumes`。不要把令牌放到进程级表上，另一个会话的 `when` 现在看不到这个 `ec_`。
- 已同意的 `fd_`：失败路径不调用 `propose_tool_goal`。保持这样。一旦改成整工具过线，已有规则会要求换一份完全不同的 schema，前面已经通过的步骤会一起废掉。

### 3. 已批准的 bash 命令会被上一步输出改写

批评第 16 条要求槽位值经 `shellQuote` 进入命令，脚本等于观察到的命令。批评第 8 条要求上一步输出出现在下一步参数里时必须写成边。

提议时的检查做到了：另一份脚本 `echo fixed` 会被 `script-mismatch` 拒绝。槽位替换走 `fillTemplate`，会加引号。

装上之后的边绑定没有走 `shellQuote`。`installCompiled` 把轨迹里的 `sample` 抄进存下来的边。`buildCall` 在填完模板后，用 `split(sample).join(上一步输出)` 替换命令正文。`compiledDefinition` 把内层结果交给 `presentDelegated`。退出码是 0 且正文里还没有退出码行时，它会接上 `\n[exit code: 0]`。`liveOf` 把这整段当成上一步输出。

行为：观察到的两步是 `echo hello`（输出 `hello`）和 `cat hello.txt`。边是 `{ path: "command", sample: "hello" }`。按插件的委托包装执行后，第二条命令变成：

```text
cat hello
[exit code: 0].txt
```

批准卡上的脚本仍是 `cat hello.txt`。输出里若带单引号，同一条替换会把引号原样嵌进命令；用输出 `hello'BREAK` 直接喂执行器时，第二条是 `cat hello'BREAK.txt`。

次生影响：

- 审批：用户同意的是卡片上的模板。运行命令可以在同意之后变成另一条。修的时候要改执行器里的边替换，不要把卡片再截成一行。
- 已同意的 `fd_`：`smoke.mjs` 要求委托结果里保留 `[exit code: 0]` 和「已覆盖」。`ownedDefinition` 在缺槽位时仍返回 `invalid arguments` 且 `failed: false`。不要改 `presentDelegated` 或 `fillTemplate` 的返回形态来修编译边。编译执行器应停止把这段包装正文嵌进 shell。
- 摩擦记分：被改写的内层 bash 走 bypass，不计分。命令跑坏了也不会把 bash 过线。
- 会话隔离：边和 `sample` 在会话目录的 catalog 里。不要为了修替换去重放原工具。

### 4. 两段无关的 bash 会粘成一个程序，装上后任意 bash 都被拦截

批评第 3 条要求常量值不同就是另一份程序，全参数都是槽位且原样调用原工具的片段不入库。批评第 6 条要求跨过两次完整重复接缝的窗口丢掉，短片段若是更长成熟片段的连续子串就不写入 `compilable`。批评第 5 条要求常量对不上就放行原工具。

工具名不同时，第 6 条的接缝是生效的：`read` → `grep` → `bash` 重复两次，`matureFragments` 只返回这一条。

工具名都是 bash 时不生效。轨迹是 `ls /tmp`、`pwd` 重复两次，再接 `ls /var`、`whoami`、`date` 重复两次。返回的唯一片段有 5 个 bash 步，两次出现分别是：

- `ls /tmp`、`pwd`、`ls /tmp`、`pwd`、`ls /var`
- `whoami`、`date`、`ls /var`、`whoami`、`date`

模板是 `{{p0_command}}`、`{{p1_command}}`、`ls {{p2_command_0}}`、`{{p3_command}}`、`{{p4_command}}`。真正重复过的两步和三步被 `isSubsequence` 按工具名丢掉。`allSlotPassthrough` 没挡住它，因为中间那步还有一个 `ls` 模板常量。

第一步的常量列表是空的，只有一个字符串槽位。`interceptMatches` 对 `pwd` 和 `ls /tmp` 都返回 true。这份片段一旦安装，当前会话里任意带字符串 `command` 的 bash 都会被拒绝，并改走这一个 `ec_`。

次生影响：

- 摩擦记分：这些调用都是成功，不加分。修片段时把它们记成失败，会把 bash 推向过线，已有 `fd_` 后继会按 `look()` 压过编译拦截。
- 审批：技能要求模型沉淀 `compilable` 里最长的片段。用户会看到一份从未完整重复过的五步合同。
- 会话隔离：拦截仍应只留在当前会话。另一个会话的 `when` 现在看不到 `ec_`，这项不要改成进程级拒绝。
- 已同意的 `fd_`：bash 已有后继时，`look()` 返回的 `intercepts` 是空的，直接调用走 `fd_`。还没有 `fd_` 时，这份错误拦截会吃掉所有 bash，用户也进不了 `propose_tool_goal`，因为拦截发生在摩擦过线之前。
- 桌面开关：关掉的是 bundle，会话目录还在。重新打开会把这份拦截装回来。不要用清空 `friction-drive/sessions` 来做开关，那里还有已经同意的 `fd_`。

### 5. 编译改动不在 GitHub 上，现有测试却能全绿

批评第 13、17 条要求：第三方入口单独测；必须带能访问 GitHub 的代理，以及父进程里的 `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_0`、`GIT_CONFIG_VALUE_0`；子进程若仍删掉名字含 `KEY` 的变量，断言失败原文是 `missing config key GIT_CONFIG_KEY_0`，profile 的 bundles 里不得出现本插件，不得记通过。做不到的条目标成失败，不得改成备注。

工作区没有这个用例。`compiler.test.js` 开头写着「不启动桌面端」。那一句是备注，测试文件自己仍以通过结束。

`github:Zbcc0826/dsh-friction-drive` 指向的 `main` 没有 `compiler.js`。桌面上用「安装第三方插件」装到的是 `cee6600` 的旧插件：没有 `propose_compiled_procedure`，没有 `ec_`，卡片标题也还不是工作区里改过的「经验编译」。`node install.mjs` 用 `link:` 指到这份工作区，和 GitHub 克隆不是同一个树。用脚本成功代替第三方安装，正是批评禁止的替换。

本机直连 GitHub 会超时这件事没有被测试。代理端口 `7890` 开着，但本进程没有代理环境变量。插件和 `install.mjs` 都不负责桌面端那次 `git clone`。

次生影响：

- 桌面开关：开关认的是 profile 里的 bundle 名 `dsh-friction-drive`。名字没改，这项是对的。开关切的是已经装上的那一版。在推送之前去拨开关，拨的是旧插件，不能用来证明 `ec_` 或新标题。

## 高

### 6. 已登记工具的参数错误不进入轨迹

批评第 7 条要求每一次调用都留下记录，已登记工具可以当断点，不得进入 `compilable`，也不得被序列拦截。

`index.js` 的 `observe` 在 `registry.has(工具名)` 时直接返回，不调用 `ingestCall`。示例工具只在自己的 `execute` 里调用 `friction.record`。Harness 在 `execute` 之前就拒绝的参数错误没有这条 `record`。

行为：同一会话里对 `bash ls /tmp`、`fx_convert` 的参数错误、`bash pwd` 做两轮，并且 `fx_convert` 只发 `post-execute`、不进 `execute`。`friction_status.compilable` 是 `[["bash","bash"]]`。`fx_convert` 没有分数记录。中间那次参数错误没有切断 `ls` 和 `pwd`。

随后真正 `execute` 一次单位非法的 `fx_convert`，分数是 3，调用次数是 1。`record` 记了一次，`observe` 没有再记一次。双计被避开了，断点也一起被避开了。

次生影响：

- 摩擦记分：去掉 `observe` 里的跳过，会和 `execute` 里的 `record` 各记一次。`ledger_lookup`、`fx_convert`、`window_overlap` 会以大约一半的次数过线。修法是只补一条 `registered: true` 的轨迹断点，不要再调用 `noteCall`。
- 已同意的 `fd_`：这三个名字在 registry 里，不在 `fd_` 的 successor 上。补断点不会改 `fd_` 的名字或 schema。
- 序列拦截：登记工具现在进不了片段，所以也不会成为拦截的第一步。补上断点之后仍然不能让它们进入 `compilable`。

### 7. 失败步不能换成新脚本，原脚本对着旧成功却能再通过

批评第 9 条允许只重提失败那一步的 `run`、前置或后置，其他步改了就拒绝。新版本要通过独立验收。

其他步的锁定有测试。失败步自己的 `run` 仍要等于观察到的 `commandTemplate`。`echo two` 改成 `echo fixed` 时，原因是 `script-mismatch`。把原来的 `echo two` 再交一次，返回 `REVISE`，名字仍是原来的 `ec_`。验收用的是 `spec.bindings`，也就是当初两次成功，不是刚刚失败的那次输出。

次生影响：

- 审批：同一份会失败的脚本可以再要一次同意，卡片看起来像一次修复。
- 摩擦记分：修订通过后仍不计整工具摩擦。不要为了「真的失败过」去给 `ec_` 加失败分。
- 已同意的 `fd_`：修订走 `stageCompiledRevision`，要等会话提交才换上。这和 `fd_` 的「本轮仍用旧版」一致。不要把失败步的立即降级改成删除整个 `fd_` 或 `ec_`。

### 8. 两次输出不同，只要退出码是 0，这一步仍是 program

批评第 10 条要求后置只能引用已经保存的字段，两次参照不一致就不得标成 `program`。签名至少还要包含前置和后置。前置只能引用轨迹里已经出现的字段。

`structuralKey` 的对象只有 `tools`、`constants`、`slots`。`judgePre` 允许 `{}` 和 `{ argsEquals: ... }`，不比较 `argsEquals` 和两次参数。执行器不读 `pre`。字符串里出现 `env`、`cwd`、`directory`、`workdir`、`环境` 才会被拒绝，所以命令正文 `printenv` 会因为子串被拒，路径 `/not/observed` 会通过。

行为：`echo same` 两次输出分别是 `alpha` 和 `beta`，退出码都是 0。`contractFor` 生成的后置是 `{ exitCode: 0 }`，评估结果是 `READY`。空后置会被拒绝，这项只堵住了恒真，没有堵住「参照不一致」。

次生影响：

- 审批：卡片里的「两次绑定」目前只被退出码撑着。输出不同的步骤仍会变成会执行的程序步。
- 摩擦记分：这是成功调用，不加分。
- 会话隔离：资产的 `structuralKey` 存在会话 catalog。把前置后置加进键之后，旧的测试资产对不上，不影响已同意的 `fd_`，因为 `fd_` 不读这个键。
- 已同意的 `fd_`：不要把 `judgePre` 的子串黑名单套到 `fd_` 的 `problem` / `usage` 上，那里可以出现目录和环境的说明。

### 9. 正文里的非零退出码不计摩擦失败

批评第 1 条要求正文匹配 `[exit code: 非0]` 时也算失败，并且不能进入成功轨迹。

成功轨迹这边做到了。`classifyCall` 用 `commandFailed`，`eligible` 为 false。`compiler.test.js` 锁了「正文退出码和截断都不成熟」。

记分没有跟着改。`index.js` 把 `failureOf` 的 `ok` 传给 `ingestCall`，`failureOf` 不看正文。`test.js` 仍断言：数值退出码是 0、正文含 `log [exit code: 1]` 时，`failureOf` 为成功。

行为：

- 数值退出码 0，正文含 `[exit code: 1]`：不能进片段，摩擦分 0，`failures` 为 0，`lastOk` 为 true。
- 没有数值退出码，正文是 `[exit code: 1]`，调用方仍传 `ok: true`：记录上的 `failed` 为 true，摩擦分仍是 0。

次生影响：

- 摩擦记分：若改 `failureOf` 去看正文，`test.js` 那条会破。日志里的退出码字样会给 bash 加失败分，连续三次正文命中就可能过线。bash 上已有的 `fd_` 后继会压过编译拦截，这段成功轨迹不再进入 `compilable`。
- 已同意的 `fd_`：缺槽位的 `invalid arguments` 必须继续不计分。`ingestCall` 对 `invalid` 跳过记分，这项要留着。
- 编译轨迹可以继续比记分更严。两边不要合成一个 `failureOf`，除非同时改掉「数值退出码优先于正文」的旧测试，并接受 bash 更快过线。

### 10. 仓库外测试没有加载插件入口

批评第 13 条要求干净目录里，除了安装脚本 vendor 出来的 `@deepseek-ai/dsh-tools`，没有别的解析路径；插件能加载；加载失败不得记成安装成功。关掉的是 bundle `dsh-friction-drive`，关完后 `friction_status` 和 `ec_` 都不可调用。

`compiler.test.js` 的「仓库外」用例把六个源文件拷进临时目录，再把本仓库的 `locale/zh.json` 拷进去读回标题，然后把 `.dsh-deps/node_modules/@deepseek-ai/dsh-tools` 符号链接进临时 `node_modules`，最后只 `import` 临时目录里的 `schema.js`。

这证明 `schema.js` 能从这条符号链接读到 `defineTool`。它不证明：

- `index.js` 能在没有仓库 `node_modules` 的目录里加载。

- 第三方安装或关掉 bundle 之后工具是否还在。

`.dsh-deps` 被 git 忽略。没有跑过 `install.mjs` 的克隆上，这条符号链接的目标不存在，用例会在链接时抛错。那是本地目录缺失，不是干净安装失败被记成失败。

次生影响：

- GitHub 安装：不要把 `node_modules` 或 `.dsh-deps` 提交进仓库来让这条测试变绿。桌面若自己提供 peer，会和仓库里的另一份同时存在。
