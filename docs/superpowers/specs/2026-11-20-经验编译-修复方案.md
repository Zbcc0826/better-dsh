# 经验编译修复方案

日期：2026-11-20。对照 `docs/superpowers/specs/2026-11-20-经验编译-实现挑刺.md` 的实际轨迹，不把设计句子当成已经修好。先写不变量，再改代码。

插件能保住的，只是本进程里已经记下的参数、正文、退出码和文件哈希。审批前不调用原工具。下面每条都写：要保住的不变量、最小改动、会牵动哪些已有机制。牵动范围只从这些里挑：记分、审批、会话隔离、已同意的 `fd_`、拦截、恢复令牌、桌面开关、GitHub 安装。没写到的那几项，这条改动不动它们。

宿主限制写在文末。插件不能把那些失败记成自己已经修好。

## 总原则

一步要变成会执行的 `program`，必须同时满足：

- 脚本或委托就是这次轨迹里观察到的那次调用，不是另一条命令。
- 后置只引用已经保存的正文、退出码、截断标记、失败标记、文件哈希。
- 两次保存的正文相同。正文不同时，退出码都是 0 也不能当 `program`。
- bash 的槽位和上一步正文嵌进命令时走现有 `shellQuote`。
- 不是 bash 时，工具必须是只读名单里的（`read`、`grep`）。效果就是已保存正文，或两次文件哈希一致。`write` 以及名单外的工具保持 `agent`，执行器不得调用原工具。

未知工具默认不是只读。插件没有隔离重放环境，不能把「也许没副作用」说成可以自动执行。

## 致命

### 1. 非只读写入不得成为 program，也不得按未观察槽位调用原工具

不变量：用户同意的是「这两次已经发生过的调用，其效果能用保存下来的正文或哈希验收」。`write` 的效果是改文件，返回的 `ok` 证明不了文件内容。审批通过后，执行器不得用观察里没出现过的槽位去调用 `write`。

最小改动：

- `compiler.js` 增加只读名单。`checkRun` / `validateProgram` 在 bash 之外，工具不在名单里就返回 `STEP_MUST_BE_AGENT`，理由 `not-readonly`。不调用原工具。
- `contractFor` 对这种步生成 `agent`，不生成 `delegate` 程序步。整份合同没有 `program` 步时返回 `NOT_A_PROGRAM`，不安装、不写拦截。
- `executeCompiled` 在 `invoke` 之前拒绝非只读委托，返回 `NOT_PROGRAM`。`index.js` 只把该步标成 `agent`，不调用 `noteCall`。

牵动：

- 记分：不把写入失败送进 `noteCall`。否则三次失败会把 `ec_` 或原工具过线，而 `propose_tool_goal` 又拒绝整份替换 `ec_`。
- 审批：这种合同不再以两步都是 `program` 的形式通过。卡片只在评估返回 `READY` 或 `REVISE` 之后才弹出。
- 会话隔离：不改。拦截仍只在当前会话的 `catalog.intercepts`。
- 已同意的 `fd_`：不把编译拦截写进 `successor`。`look()` 在已有后继时仍让 `fd_` 优先。
- 拦截：不安装「全是 agent」的写入合同，避免第一步常量把 `write` 拦死、`ec_` 又执行不了。
- 恢复令牌、桌面开关、GitHub 安装：不改。

### 2. 恢复必须对照已保存后置；失败步不能靠旧脚本再被批准

不变量：模型交回来的正文，必须能由该步已经保存的后置直接判定。对不上就停，后面的程序步一次都不执行。失败步在新的独立验收通过之前保持 `agent`。把原来的失败脚本再交一次，不是新验收。

最小改动：

- `executeCompiled` 恢复时只解析模型交来的正文。正文里有 `[exit code: N]` 才采用这个退出码。不再造一份 `exitCode: 0` 去套后置。空后置的显式模型步仍可继续（现有「中间 read 留给模型」的合同后置就是空的）。
- 对不上返回 `POST_FAILED`，不进入后面的循环。
- `assessRevision`：失败步的脚本与已失败的 `run` 相同，返回 `NOT_REVISED`，不返回 `REVISE`。其他步的脚本、常量和边仍是 `STEP_LOCKED`。
- 失败步可以交另一份 bash `run`。验收只看已保存的两次绑定：后置必须成立，并且必须钉住正文（`outputIncludes` 或 `fileHash`），不能只写退出码。评估函数不执行新脚本。写入类工具换了 `run` 仍是 `not-readonly`，不能变成 `program`。

证明不了的部分：新脚本没有被重放。已保存参照只证明旧两次输出满足后置，不证明新脚本会产生那段输出。所以新脚本必须原样出现在审批卡上；用户不同意就不写入目录。插件不能把这一步说成已经重放通过。

牵动：

- 记分：恢复失败和 `NOT_REVISED` 都不调用 `noteCall`，不给整个 `ec_` 加摩擦分。
- 审批：同一份失败脚本不能再要一次同意。另一份脚本只有评估通过后才弹出卡片。
- 会话隔离：`resume_token` 仍只写在该会话的 `state.resumes`。
- 已同意的 `fd_`：不调用 `propose_tool_goal`，不删除 `fd_`。
- 拦截：失败降级只改该步 `mode`，不改 `intercepts`，也不把拦截写进 `successor`。
- 恢复令牌：对不上后置时不发放新的继续权，不执行后续命令。令牌仍不进进程级表。
- 桌面开关、GitHub 安装：不改。

### 3. 上一步正文嵌进 bash 必须经 shellQuote

不变量：用户批准的是卡片上的那条命令。上一步输出若要嵌进下一步 bash，只能替换已记录的样本，并且经过现有 `shellQuote`。不得把 `cat hello.txt` 改写成带换行和 `[exit code: 0]` 的另一条命令。输出里的单引号不得裸嵌。

最小改动：

- 只改 `compiler.js` 的 `buildCall` / `liveOf`。`presentDelegated` 和 `fillTemplate` 不改。`smoke.mjs` 仍要求 `fd_` 委托结果保留 `[exit code: 0]` 和「已覆盖」。
- 执行器认出委托包装：正文末尾的退出码行和「已覆盖」不参与替换。剥掉之后若与样本相同，命令保持批准时的原文。
- 与样本不同时，用 `shellQuote` 替换，不再 `split(sample).join(上一步正文)`。
- `compiledDefinition` 把内层工具的原始正文和 `value.exitCode` 交给执行器，不把 `presentDelegated` 的包装正文交给边绑定。

牵动：

- 记分：内层 bash 仍走 bypass，不计分。命令不再被包装正文改写，因此也不会因为改写后的失败把 bash 过线。
- 审批：不把卡片再截成一行。改的是执行器，不是卡片文案。
- 会话隔离：边和样本仍在会话 catalog。
- 已同意的 `fd_`：不改 `ownedDefinition` 的返回形态。
- 拦截、恢复令牌、桌面开关、GitHub 安装：不改。

### 4. 无关 bash 不得粘成一个程序；没有常量的第一步不得拦截全部 bash

不变量：两次出现要是同一段程序，每一步都得有观察到的常量。整段命令都变成一个字符串槽位，只说明工具名都叫 bash，不是同一条程序。常量不同的短程序，不得因为工具名序列是更长片段的子串就被丢掉。拦截必须对得上第一步常量；第一步没有常量时，不得拒绝任意 bash。

最小改动：

- 对齐结果里任一步没有常量，就不是同一次重复，不写入 `compilable`，也不当成接缝。
- 丢掉短片段时，比较的是连续步上的常量值，不是工具名。`read → grep → bash` 这种常量相同的真子串仍只保留最长的一条。
- `interceptMatches`：第一步常量列表为空则返回 false。

这样 `ls /tmp`、`pwd` 与 `ls /var`、`whoami`、`date` 不会合成 5 步。真正重复的两步和三步各自留下。`pwd` 不会因为有人装了一份「命令整个是槽位」的合同就被所有 bash 命中。

牵动：

- 记分：这些调用仍是成功，不加分，避免把 bash 推向过线后让已有 `fd_` 压过编译拦截。
- 审批：技能只会看到真正重复过的片段，不会看到一份没完整重复过的五步合同。
- 会话隔离：拦截仍只在当前会话。另一个会话的 `when` 仍看不到这个 `ec_`。
- 已同意的 `fd_`：不改 `look()`。已有后继时编译拦截仍是空的。
- 拦截：无常量的第一步不再匹配所有带字符串 `command` 的 bash。有常量的 `ls /tmp` 仍只命中这条命令。
- 恢复令牌：不改。
- 桌面开关：不改。关掉的是 bundle，不清理 `friction-drive/sessions`。错误拦截本来会在重新打开时被装回来；修的是不要生成这份拦截，不是删目录。
- GitHub 安装：不改。

### 5. 编译改动不在 GitHub 上

不变量：第三方入口 `github:Zbcc0826/dsh-friction-drive` 的 `main` 在推送之前仍是没有编译器的旧树。工作区未提交、本地 `link:`、`node install.mjs` 成功，都不能写成这个入口已经通过。

最小改动：不改安装脚本，不伪造 profile，不把超时改成成功。本方案不提交、不推送。

牵动：

- GitHub 安装：修不好。见文末宿主限制。推送之前，克隆结果不会出现 `compiler.js`。
- 桌面开关：开关认的是 bundle 名 `dsh-friction-drive`。名字保持不动。推送并重启之前，拨开关看到的仍是旧插件，不能用来证明 `ec_` 或新标题。
- 已同意的 `fd_`：即使以后推送，也不迁移、不清空 `friction-drive/sessions`。
- 记分、审批、会话隔离、拦截、恢复令牌：这条没有代码可改。

## 高

### 6. 已登记工具的参数错误必须切断轨迹

不变量：`fx_convert`、`ledger_lookup`、`window_overlap` 以及 `registry` 里的工具可以出现在轨迹里当断点，不得进入 `compilable`，不得被序列拦截。Harness 在 `execute` 之前拒绝的参数错误也是断点。这条断点不得再记一次摩擦分。

最小改动：

- `observe` 见到已登记工具时追加 `registered: true` 的轨迹记录，不调用 `noteCall`。
- `execute` 里的 `record` 仍负责那一次记分。同一 `callId` 的 post-execute 不再追加第二条。示例工具把 `callId` 传给 `record`，只为了认出这一次，不改 schema，不改工具名。
- 参数错误只有 post-execute、没有 `execute` 时，轨迹上仍有这一条断点，分数不变。

牵动：

- 记分：不第二次 `noteCall`。`ledger_lookup` 不会因为补断点而提前过线。缺槽位的 `invalid arguments` 仍走 `ingestCall` 的 invalid 跳过，不计分。
- 已同意的 `fd_`：这三个名字不在 `fd_` 的 successor 上。断点不改 `fd_` 的名字或 schema。
- 拦截：登记工具仍不能成为 `compilable` 的一步，也不会变成拦截的第一步。
- 会话隔离：断点写在当前会话轨迹里。
- 审批、恢复令牌、桌面开关、GitHub 安装：不改。

### 7. 失败步的新 run 对照已保存参照，旧脚本再交一次不是修订

不变量与致命第 2 条是同一件事，这里写修订一侧：其他步的脚本、常量和边不能改。失败步的新 bash 脚本可以不同于旧模板，但后置必须能由两次已保存的正文和退出码判定，并且要钉住正文。脚本等于旧模板就通过，这条删掉。

最小改动：在 `assessRevision`，不在 `propose_tool_goal`。通过后仍走 `stageCompiledRevision`，本轮提交前用旧合同。

牵动：

- 审批：旧脚本不再得到 `REVISE`。新脚本评估通过后才有卡片。
- 记分：修订通过后仍不计整工具摩擦。
- 已同意的 `fd_`：不删除，不整份替换。
- 会话隔离、拦截、恢复令牌、桌面开关、GitHub 安装：不改。

### 8. 两次正文不同，不得只靠退出码 0 成为 program

不变量：程序步的两次参照要一致。正文不同，就不是能独立验收的同一步。签名除了工具名、常量、槽位，还带上由这两次保存结果推出的后置。前置里声称的 `argsEquals` 必须在两次参数里都出现；对不上就不得为 `program`。

最小改动：

- `canBeProgram` 要求两次 `output` 全等。`postFor` 在正文不一致时不生成 `{ exitCode: 0 }`。
- `structuralKey` 加入这份后置。常量不同本来就不是同一把钥匙；后置不同也不再撞同一把钥匙。`fd_` 不读这把钥匙。
- `judgePre` 增加对照绑定。目录、环境的子串黑名单仍只用于编译合同的 `pre`，不套到 `fd_` 的 `problem` / `usage` 上。

牵动：

- 记分：这是成功调用，不加分。
- 审批：正文不一致的步不会以 `program` 出现在卡片上。
- 会话隔离：钥匙仍在会话 catalog。旧测试资产用同一个函数现算，不迁移磁盘上的 `fd_`。
- 已同意的 `fd_`：不读 `structuralKey`，不受影响。
- 拦截、恢复令牌、桌面开关、GitHub 安装：不改。

### 9. 正文里的非零退出码记摩擦失败

不变量：正文匹配 `[exit code: 非0]` 时，这一次是摩擦失败。`lastOk` 不得仍为成功，摩擦分不得为 0。参数错误（错误信息里的 `invalid arguments`）仍然不计分。成功的同参重复不加 retry 分：retry 只加在「上一次失败，而且这一次仍失败」的同参调用上。因此正文失败把 `lastOk` 打成 false 之后，下一次真正成功的同参调用不会多出 retry 分。

最小改动：

- `failureOf` 在放过 `invalid arguments`、看过 `isError` / `value.failed` / 数值退出码之后，再用 `commandFailed` 看正文。数值退出码是 0 不再压过正文里的非零退出码。
- `ingestCall` 用轨迹上的 `failed` 决定记分用的 `ok`，这样直接记账而调用方仍传 `ok: true` 时也会记失败。
- `scoreCall` 的 retry 增加 `event.ok === false`。失败后再失败的同参重试、verbose 叠加保持不变。成功五次仍是 0 分。

次生影响要接受的部分：bash 连续三次正文失败会过线（失败权重 3，阈值 8）。过线后若该工具已有 `fd_` 后继，`look()` 仍让后继优先，编译拦截不参与。这不是把成功调用重新记成 retry。

不改的部分：截断和慢调用仍加分。编译轨迹继续用 `classifyCall`，比记分更严的断点（截断、参数错误、本插件工具）保持原样。

牵动：

- 记分：这是这次要改的记分。不改阈值，不改权重表。
- 已同意的 `fd_`：缺槽位仍不计分。过线后的优先顺序不改。
- 审批、会话隔离、拦截、恢复令牌、桌面开关、GitHub 安装：不改。拦截不因为这次记分被写进 `successor`。

### 10. 仓库外测试必须加载插件入口

不变量：干净目录里，插件入口是 `index.js`。`@deepseek-ai/dsh-tools` 解析不到，这次加载就是失败，不得记成安装成功。只导入 `schema.js`，或把测试自己拷进去的 `locale/zh.json` 读回来，都不能证明入口能加载。

最小改动：改 `compiler.test.js` 的仓库外用例，对临时目录里的 `index.js` 做 `import`。解析抛错则用例失败。不断言 GitHub 安装成功，不断言桌面开关已经关掉工具。

证明不了的部分：

- 桌面卡片的中文名来自宿主读安装后的 locale，不是 `index.js` 的导出。本用例不把读到标题写成安装成功。
- 关掉 bundle 之后 `friction_status` 和 `ec_` 是否还能被调用，要在桌面上看。插件没有卸载钩子，也不会删除 `friction-drive/sessions`。
- 宿主的加载器是否从应用自己的依赖里解析 peer，本仓库的符号链接证明不了。链接目标不存在时，用例失败。

牵动：

- GitHub 安装：不把 `node_modules` 或 `.dsh-deps` 提交进仓库来让用例变绿。
- 桌面开关：不改 bundle 名，不删会话目录。
- 已同意的 `fd_`：目录留在磁盘上。再次打开仍按目录挂回，这不是本用例要「修」的行为。
- 记分、审批、会话隔离、拦截、恢复令牌：不改。

## 明确不改

- 包名 `dsh-friction-drive`，`cordis.patch.yml` 的 insert，`install.mjs` 的 `bundleName`，导出的 `name`，技能注册名 `friction-drive`，状态目录 `friction-drive/sessions`。
- `presentDelegated`、`fillTemplate`、`ownedDefinition` 的返回形态。
- 把编译拦截写进 `successor`，或在已有 `fd_` 后继时仍应用编译拦截。
- 为了拦截写入去改全局工具表，或清空 `friction-drive/sessions` 来模拟关开关。

## 宿主限制，插件不能假装修好

这些不是 `compiler.js` 能修的。本轮不写通过记录，不启动桌面端，不读取密钥，不提交，不推送。

1. 「安装第三方插件」里的 git 由桌面端拉起。Harness 若按名字删掉含 `KEY` 的环境变量，子进程只剩 `GIT_CONFIG_COUNT`，git 以 `missing config key GIT_CONFIG_KEY_0` 退出，profile 的 bundles 里不该出现本插件。`install.mjs` 不跑这次 git。往插件里加 git 包装也改不到宿主的子进程。
2. 本进程没有 `http_proxy` / `https_proxy`。直连 `github.com` 超时是网络事实。`127.0.0.1:7890` 只说明这台机器上有代理端口，不说明桌面端的 git 使用它。插件不得在超时后自己把 bundle 写进 profile。
3. 无界面时是否立刻 `NOT_APPROVED`，取决于宿主的 `approval.request` 是否返回 `unavailable` 或拒绝。插件继续等这个调用。加一个短超时会把还没点的真卡片砍掉。宿主若挂起，那是用例失败，不是插件改返回值就能变成同意。
4. GitHub 克隆没有 `node_modules`。`@deepseek-ai/dsh-tools` 是 peer。宿主加载器从哪里解析它，要用真实的第三方安装看。仓库外用例只证明：在测试准备的解析路径上，`index.js` 要么加载，要么失败。
5. 关掉开关是宿主卸下 bundle `dsh-friction-drive`。会话目录还在，里面有已经同意的 `fd_` 和将来的 `ec_`。插件不在卸载时删除这个目录。
6. 工作区里的编译器在推送到 `github.com/Zbcc0826/dsh-friction-drive` 的 `main` 之前，第三方下载到的仍是旧插件。未提交不等于下载流程已通。
